# Phase 1 production hardening

Date: 2026-07-28
Status: code hardening implemented; independent/manual release evidence pending

## Scope

Phase 1 prepares the restricted Solana desktop lanes for production acceptance:

- Jupiter Solana Swap;
- Pump.fun Token Launch.

It does not activate EVM, Bridge, autonomous execution, or approval-bypass Full
Access.

## Implemented in this phase

### Provider resilience

- Jupiter operations use a circuit breaker and a 120-request/60-second sliding
  budget.
- general Solana RPC and Pump launch RPC use separate 240-request/60-second
  sliding budgets;
- every retry consumes budget, so a sustained partial outage cannot create an
  unbounded retry stream;
- exhaustion blocks before `fetch`, does not invent fallback evidence, and is
  recorded with a sanitized machine-readable audit event;
- mutation/broadcast paths remain single-attempt.

### Program policy

- Jupiter Swap and Token Launch derive program allowlists from one
  release-controlled manifest;
- every address records its lane, narrow capability, and rationale;
- tests prove Pump launch authority cannot leak into Jupiter Swap and Jupiter
  routing authority cannot leak into Token Launch;
- the change process is documented in
  [Solana program allowlist change control](desktop/SOLANA_PROGRAM_ALLOWLIST.md).

### Reconciliation evidence

- finalized/confirmed Solana RPC evidence remains authoritative over router
  status;
- router-failed/RPC-confirmed and router-success/RPC-failed contradictions
  produce explicit sanitized audit codes;
- a contradiction never triggers rebroadcast or a synthetic success.

### Safe diagnostics

- audit events accept only bounded machine-readable fields;
- the desktop writes JSONL diagnostics under its local user-data logs folder;
- files rotate at 1 MiB with at most three retained archives;
- filesystem errors cannot interrupt custody, policy, or reconciliation;
- secrets, provider bodies, prompts, signed transactions, and arbitrary error
  strings have no field in this logging contract.

## Automated evidence

Automated tests cover rate-budget exhaustion before network I/O, cooldown
recovery, lane-separated program manifests, evidence contradictions, bounded
log fields, and finite log rotation. These checks supplement the existing
simulation, fee guard, one-signature, one-broadcast, receipt, encrypted restart
recovery, tamper detection, and emergency-stop suites.

Validated on 2026-07-28:

- typecheck passed for every workspace;
- 337 automated tests passed: 11 cloud-worker, 317 desktop, and 9 web;
- lint passed;
- production builds passed for cloud-worker, desktop, and web;
- the desktop privilege and Pump.fun production-boundary audit passed;
- the Next.js production build generated all 28 web routes successfully.

## Evidence still required

These cannot be honestly generated by application code:

1. independent private-key/vault lifecycle review;
2. clean-profile backup and recovery drill;
3. manual audit of Windows crash/event/diagnostic artifacts;
4. production Authenticode credentials and signed installer;
5. clean-machine install, upgrade, rollback, uninstall, and vault-retention
   tests;
6. controlled minimum-value Jupiter Swap acceptance;
7. controlled minimum-outflow Pump.fun Token Launch acceptance;
8. independent security review with redacted evidence digest and reviewer.

Until those items pass, the correct status is **production candidate**, not
general production-ready.
